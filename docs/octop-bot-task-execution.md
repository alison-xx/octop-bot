# Octop Bot 任务执行设计：在哪做、谁来做、怎么做好、怎么交付

> T0–T3 的首批实现已通过 #36、#48 进入 main。各期已做和待做项见 §12.1–12.4。2026-11-25 已批准启动 T4，见 §13。本文承接 [云端方案](octop-bot-cloud-plan.md) §12.4–12.7。

## 0. 结论先行

1. **执行位置有三个，按「能不用电脑就不用」排序。** 不用电脑（连接器、搜索、写作）优先，其次是云电脑，最后才是用户自己的电脑。云电脑是默认的干活地方；本机只接「只有这台电脑才有」的东西：本机文件、本机应用、内网、连着的设备。
2. **位置由规则先筛、模型再选，不加一层路由模型。** 服务端按用法、Bot 设置、隐私、余额、设备在线和任务来源算出这一回合能用哪些位置，把结果写进系统提示并只暴露对应工具。这部分是确定性的，可以用真值表测试。
3. **灵策用法下，Bot 现在够不到本机。** 桌面登录灵策后窗口直接连云端（cloud-plan §12.10），本机能力全部不可用。要让云端的 Bot 用这台电脑，需要新做「本机连接」（§3.5），这是本文最大的一块新工程，需要你拍板（§13 Q1）。
4. **人的参与分四种，各有固定触发条件。** 提问（需求不清）、确认（有后果的动作）、接管（Bot 做不了或不该做）、介入（用户主动看、打断、停止）。密码、验证码、扫码、付款、实名一律接管，Bot 不尝试。
5. **没人在场时不失败、不硬闯，而是挂起。** 定时任务或 IM 发起的任务遇到接管或确认，任务进入「等你」，云电脑暂停停止计费，推送到手机，最多等 24 小时。现在的行为是直接报错（§1 缺口 4）。
6. **质量靠「任务契约 + 证据 + 看门狗」，不靠提示词里一句「请认真」。** 每个任务有目标、可检查的验收条件和步骤；每条验收条件要有证据才能标完成；没验证过就不能宣布完成。群聊 Goal 已经是这个模型（`infra/bot_groups/service.py`），私聊任务复用它。
7. **产物必须显式交付，交付前自动检查。** Bot 用 `publish_file` 交付，服务端检查文件能不能打开、有没有内容，并生成缩略图。对话里是产物卡片，最后一条消息是「交付单」：逐条验收结果、没做完的、花了多少。
8. **界面保持现在的克制：一个任务一张卡。** 工具步骤继续不刷屏，标准以上的任务用「任务卡」取代底部那行状态。需要用户的事统一成琥珀色的「需要你」卡片族，并汇总到侧栏和手机推送。
9. **动效只表达三件事：谁在操作、进展到哪、是否需要你。** 同一个对话里同时只有一个「活着」的元素。时长和缓动沿用现有样式里的取值并收成一套令牌（§8）。
10. **DeepSeek Super-agent 不能直接集成，值得借的是调度层设计。** 它是 TypeScript 写的 DeepSeek Harness 插件，Worker 以运维者的系统用户身份直接跑命令，没有沙箱和审批，也没有计划与验证环节。它解决的是「请求怎么进来、怎么分派、怎么不丢」，正好补 Chief 和群聊的调度；单个任务怎么做好要靠本文 §5。

### 云端 Bot 如何选择执行位置（2026-11-26）

| 用户要的结果 | 执行位置 | 交付与验收 |
|---|---|---|
| 画图、同主题多张图、做短视频 | Octop 服务端调用灵策 API。同主题 2～4 张优先一次提交；不同脚本、不同场景分别传入各自的提示词。 | 逐个保存到云工作区，用实际文件数更新卡片。在会话中直接预览和下载。 |
| 按 Skill 汇总信息、调用已连接的业务系统 | Octop 加载技能说明，按其中的步骤调用当前租户已授权的连接器或 API。 | 检查接口回执、返回字段和所需文件。遇到权限、额度或参数错误时展示对应原因。 |
| 查找技能、读取附件、交付已有文件 | 用工作区工具定向读取对象存储中的技能、入站附件和成品目录。 | 从聊天卡片打开或下载文件。打开卡片无需开机。 |
| 普通 ZIP 附件解压、重新打包 | 云端工作区直接处理入站附件，保留中文目录和文件名。 | 返回独立解压目录、成员清单或新 ZIP 路径，按需读取内容并发回。 |
| Skill 需要运行二进制程序或脚本 | 使用具备该依赖的租户隔离执行环境。当前云 Bot 的 shell 在自己的云电脑中运行。 | 合并相邻的解包、转换或校验步骤，保存成品后结束。 |
| 登录网页、操作桌面软件、处理只能在机器上打开的文件 | 用租户云电脑。能用程序完成的步骤先用程序；需要界面时再读取界面元素和操作控件。 | 后台活动显示为小状态条。用户打开画面或需要接管时才建立实时画面连接。 |

统计时保留发送指令、服务建单、成品就绪、工作区保存回执、浏览器出现文件入口五个时间点。多图分别看首张和全部交齐。只在拿到服务商进度时显示百分比，部分成功时保留已交付文件。测试中应同时断言产物可读、媒体模型正确、API 型任务没有申请云电脑算力。

若要把需要命令的 Skill 也移出云电脑，下一步是给云租户接入独立的无桌面脚本沙箱。验收覆盖租户隔离、超时与清理、输入文件映射、输出回写以及执行计费。当前通用 Docker 和 OpenSandbox 后端需要部署配置，生产租户的脚本不能在 Octop API 服务进程中直接运行。

**后续脚本执行的落地顺序**

1. 从需要脚本的 Skill 中选取只读附件、生成文件的代表样本，列出解释器、依赖和输入输出。已有连接器能够完成的步骤继续调用连接器。一个 Skill 同时包含 API 和脚本时，只把脚本步骤交给沙箱。
2. 在 octop-harness 接入已配置的 Docker 或 OpenSandbox 后端；Octop 绑定租户、Bot、会话和任务。只放入本次所需的附件和技能文件，限制执行时间与资源，按任务归集日志。命令结束后把产物写回同一工作区，记录退出码、文件清单及校验结果，再释放沙箱。
3. 先在测试租户跑成功、失败、取消、重连、重试和并发任务。验收包括不同租户文件隔离、重复回调只交付一次，以及失败后保留已经成功的产物。脚本确实需要桌面软件时标明原因，再进入云电脑。
4. 发布前后用相同模型、尺寸、张数和视频长度采样。分别比较发送到建单、建单到可取成品、可取到工作区、工作区到客户端四段的中位数和 P95；同时核对成功率、成品数、云电脑启动数和计费时长。少量人工样本单列，不作为 P95。

## 2. 参照

### 2.1 Grok Bot（官方文档，2026-11-24 读取）

| 主题 | Grok Bot 的做法 | 我们怎么取 |
|---|---|---|
| 干活的地方 | 持久云电脑是主工作区，合上电脑不影响云上的活。云电脑和用户面前的 Mac / Windows 是两回事 | 相同 |
| 本机执行 | 桌面应用可以让 Bot 在本机跑命令、读文件、在云和本机之间搬文件。默认每条命令都问，卡片显示完整命令。每台设备单独设「每次询问 / 总是允许 / 永不允许」，团队管理员可以设上限。官方建议没有明确需要就设成永不允许 | 照这个模型做「本机连接」，再加上授权文件夹和已有的应用授权 |
| 流量走本机 | 可以让云电脑的网页流量经用户的电脑出去 | 放进远期。国内平台对机房 IP 风控更严，这一项对我们比对 Grok 更有用 |
| 先连接器后浏览器 | 有对应应用时比点网页可靠；到了登录页，有连接器就走连接器 | 相同，写进能力阶梯 |
| 接管 | SSO 或 passkey、过不去的 CAPTCHA、另一台设备确认或扫码、银行卡验证、网站要求真人。用户点接管，只完成卡住的那一步，点「我完成了」 | 相同，并补上卡住和身份核验 |
| 审批 | 每个动作执行前由独立的审查模型检查，可放行、要求确认或拒绝。选项是允许一次、总是允许、拒绝。规则分「自动允许」和「先问」，冲突时先问优先 | 先做确定性规则和按钮文字预检，独立审查模型放到后面 |
| 过期 | 对话里发起的卡片不过期；定时任务等后台发起的 30 分钟过期。长时间不在会询问是否继续跑定时任务 | 对话发起不过期；后台发起等 24 小时，因为暂停的云电脑只收磁盘费 |
| 通知 | 侧栏有「需要处理」状态。桌面在用时通知留在桌面，Bot 等人超过约 3 分钟才推到手机 | 相同 |
| 安全边界 | 一个账号的所有 Bot 共用一台电脑，Bot 之间不是安全边界 | 我们每个 Bot 一台 VM，这一点更强，保持 |

Grok 官方文档没有写的：本机离线时任务怎么办、接管时用户的按键是否对模型隐藏、哪些任务不该放云电脑。这几处我们自己定（§3.6、§4.5）。

## 3. 在哪做

### 3.1 三个位置

| 位置 | 是什么 | 花费 | 适合 |
|---|---|---|---|
| 不用电脑 | 云 Octop 控制面：对话、写作、连接器和 MCP、联网搜索和读网页、知识库、记忆 | 只有模型积分 | 能用接口完成的一切 |
| 云电脑 | 这个 Bot 自己的 AGS 桌面：终端、文件、Chrome、桌面应用 | 模型积分加电脑分钟数 | 需要一台机器、但不需要「这一台」的活 |
| 本机 | 用户的电脑：授权的文件夹、授权的应用、本机网络 | 只有模型积分 | 只有这台电脑才有的东西 |

### 3.2 能力阶梯

同一个位置里，从上往下选，上一级做不了才往下：

1. 连接器或接口（邮件、日历、飞书、GitHub 等）
2. 命令和文件
3. 浏览器，按网页元素操作
4. 看屏幕、点鼠标（computer use）。实测每步约 1.6 秒，外加一张图的 token
5. 请人接管

每往下一级都更慢、更贵、更容易出错。这条阶梯写进系统提示（§3.4），也是 §11 评测里「步数」和「花费」两个指标的依据。

### 3.3 决策表

| 任务特征 | 位置 | 原因 |
|---|---|---|
| 有连接器的服务：发邮件、建日程、查文档 | 不用电脑 | 最快最稳，不开机 |
| 查资料、写报告、改文案 | 不用电脑；要生成文件时才用云电脑 | 不必要的开机是浪费 |
| 开浏览器填表、批量收集网页数据 | 云电脑 | 不占用户的电脑，可以并行 |
| 跑很久的命令、装软件、编译、处理数据 | 云电脑 | 关机也能继续 |
| 运行来路不明的脚本、打开下载的文件 | 云电脑 | 隔离，坏了重置 |
| 定时任务，手机或 IM 发起的任务 | 云电脑 | 用户的电脑不一定开着 |
| 几个 Bot 同时各干各的 | 云电脑 | 每个 Bot 一台，互不干扰 |
| 用户点名的本机文件或文件夹 | 本机读取；处理量大时经确认后传到云电脑 | 文件只在本机 |
| 只有本机装了的应用：微信、企业微信、剪映、Photoshop、Xcode、带授权的 Office | 本机 | 云电脑上没有，也登不上 |
| 内网、VPN 才能访问的系统 | 本机 | 云电脑网络到不了 |
| 连着的设备：打印机、手机、U 盘 | 本机 | 物理上只在这里 |
| 只认这台设备或这个网络的账号（机房 IP 登录会被风控） | 本机浏览器 | 远期可用「云电脑流量走本机」代替 |
| 隐私 Bot 的资料 | 只在本机，不上传 | 隐私模式的承诺 |
| 密码、验证码、扫码、付款、实名 | 人来做 | 见 §4.3 |

混合任务按步骤拆。例如「把桌面上的合同整理成对比表」：本机读文件 →（确认）传到云电脑 → 云电脑生成表格 → 交付。每次换位置，任务卡上出现一行说明。

### 3.4 谁来决定

```
① 硬规则（服务端，确定性）──► ② 这一回合可用的位置和工具 ──► ③ 模型在其中选择 ──► ④ 用户可以改
```

**① 硬规则。** 一个纯函数 `resolve_placement(...)`，输入和输出都是数据，放在 `infra/bot_tasks/placement.py`：

| 输入 | 取值 |
|---|---|
| 用法 | 本机 / 灵策智算 / 自建 |
| Bot 的「执行位置」设置 | 自动（默认）/ 只用云电脑 / 只用这台电脑 |
| 这条消息的临时选择 | 自动 / 云电脑 / 这台电脑 |
| 隐私模式 | 是 / 否 |
| 云电脑 | 未配置 / 可用 / 余额不足 / 用户正在接管 |
| 本机设备 | 没有 / 离线 / 在线，及其策略（每次询问、总是允许、永不允许） |
| 任务来源 | 对话 / 定时 / IM / 群聊 / Chief 分派 |
| 用户是否在场 | 最近 2 分钟有客户端连接，或这一回合由用户亲自发起 |

输出是这一回合暴露的工具集合，加一段写进系统提示的「执行环境」：

```
执行环境（本回合）
- 云电脑：可用，已暂停（第一次使用约 5 秒恢复，按分钟计费）
- 这台电脑「MacBook Pro」：在线，每条命令需要用户确认；可用文件夹：~/Documents/合同
- 用户：在场（桌面）
规则：能用连接器就不用电脑；默认用云电脑；只有需要这台电脑上的文件、应用或网络时才用本机；
密码、验证码、扫码、付款、实名一律 request_takeover；换位置前先说明原因。
```

工具是否可见取决于这个结果，不再取决于页面地址。这同时修掉 §1 的缺口 1 和 3。

**② 几条写死的规则：**

- 隐私 Bot：只暴露本机，没有云电脑工具，也没有上传。
- 任务来源是定时或 IM，或用户不在场：本机的「总是允许」不生效，一律要确认，也就是挂起等人（§4.5）。读了网页或群里别人的消息之后被诱导去动本机，是最需要防的情况。
- 云电脑不可用（余额不足、AGS 故障）：不自动改到本机。告诉用户原因，给一个「改在这台电脑上做」的按钮。两边的花费和隐私含义不同，不能悄悄换。
- 本机离线：不自动改到云电脑去做「需要本机」的步骤，见 §3.6。

**③ 模型选择。** 在可用范围内按能力阶梯和决策表选。不单独加路由模型：DeepSeek 的测试里（二手报道，合成负载）路由加 Worker 的读缓存 token 约为单会话的 3.8 倍，私聊里不值得。

**④ 用户改。** 两边都可用时，输入框多一个「在哪做」小标签（自动 / 云电脑 / 这台电脑），只影响这条消息。Bot 资料「电脑」一栏可以改这个 Bot 的默认值。只有一个位置可用时不显示标签。

### 3.5 本机连接（新做）

灵策用法下，Agent 循环在云端。让它用这台电脑，需要桌面客户端主动连上云端，代它执行：

```
云 Octop                                         用户的电脑
┌──────────────────────┐   出站 WSS（设备令牌）   ┌────────────────────────────────┐
│ Bot 的 Agent 循环     │◄────────────────────────│ 桌面客户端主进程：本机代理        │
│  └ 工具 local_computer│   请求：命令/文件/应用   │  ├ 本机审批卡（原生窗口）         │
│ 设备中枢 DeviceHub    │────────────────────────►│  ├ 本机策略（存本机）             │
└──────────────────────┘   结果                  │  └ 本机 Octop：命令、文件、       │
                                                 │     bot_apps 应用授权（已有）     │
                                                 └────────────────────────────────┘
```

- **配对。** 桌面登录灵策时自动登记这台设备，拿到设备令牌，存进系统钥匙串。云端窗口没有 preload，所以代理放在主进程和本机服务里，不在页面里。
- **能做什么。** 第一期：在授权文件夹里列目录、读写文件、跑命令，以及云和本机之间搬文件。第二期：应用控制，复用 `bot_apps` 的四档权限和应用白名单。
- **审批在本机做出、在本机校验。** 云端只发请求，是否执行由本机代理按本机保存的策略决定。云端被攻破或被网页内容诱导，也替用户点不了「允许」。策略可以在任何客户端收紧，放宽只能在这台电脑上操作。
- **默认每条命令都问。** 卡片显示 Bot 名字、原因、完整命令和工作目录。选项是允许一次、这个对话里同类命令都允许、拒绝、永不允许这个 Bot。设备级「总是允许」需要用户在设置里手动打开，并带一句说明。
- **授权文件夹是默认范围，不是安全边界。** 命令以用户身份运行，能碰到用户能碰到的一切，所以默认每条都问、卡片必须显示完整命令。这一点要对用户说实话，不能包装成沙箱。
- **搬文件要确认。** 卡片列出文件名、大小和方向。已设「总是允许」的文件夹可以免确认。
- **前台操作时的让位。** Bot 在前台操作应用时，屏幕边缘有一圈提示。用户一动鼠标或键盘，Bot 立即暂停并显示「你在用电脑，Bot 已暂停」，点继续才恢复。优先用后台方式（无障碍接口），它不抢鼠标。

没有复用上游 Bridge 的原因：Bridge 是两台 Octop 之间按用户名和密码建立的专家级互访，对话在专家所在的实例执行。那样本机也要跑完整的 Agent 循环并配置模型，而 Octop Bot 已经去掉了密码登录。这里只需要把单个工具调用转给设备。出站长连接和断线重连的做法可以参考 Bridge。

### 3.6 位置不可用时

| 情况 | 对话里发起 | 定时或后台发起 |
|---|---|---|
| 本机离线，这一步必须用本机 | Bot 说明原因，任务停在这一步，设备上线后给「继续」 | 任务挂起为「等你的电脑上线」，最多 24 小时，推送一次 |
| 云电脑余额不足 | 积分不足卡片（已有），并给「改在这台电脑上做」 | 这次运行记为未执行并说明原因，不改到本机 |
| 云电脑正被用户接管 | Bot 等待，任务卡显示「你在操作」 | 同左，超过 30 分钟按 §4.5 处理 |
| AGS 故障 | 自动重试 3 次后说明原因 | 同左，本次运行失败并附原因 |

创建定时任务时，如果指令里用到本机，保存前提示「这台电脑关机时这个任务会等待」。

## 4. 人的参与

### 4.1 四种形式

| 形式 | 什么时候 | 用户做什么 | Bot 的状态 |
|---|---|---|---|
| 提问 | 需求有歧义，缺关键信息，几个方向的代价差别大 | 选一项或填一句 | 等回答 |
| 确认 | 有后果的动作之前 | 允许一次 / 总是允许 / 拒绝 | 这个动作等待，其他不动 |
| 接管 | Bot 做不了或不该做的一步 | 亲手操作，点「我完成了」 | 电脑上的操作全部暂停 |
| 介入 | 用户自己想看、想改、想停 | 看画面、发消息改方向、停止 | 照常，或按用户说的改 |

### 4.2 什么时候提问

- 只在开头问一次，最多三个问题，合在一张卡片里。
- 只问会明显改变做法或结果的事。其余的写成「假设」放进计划，继续干，用户随时可以纠正。
- 没人在场的任务不提问，把假设记进交付单。

### 4.3 什么时候接管

必须接管，Bot 不尝试：

| 类别 | 例子 |
|---|---|
| 身份凭据 | 密码、短信或邮箱验证码、动态口令、passkey、单点登录、扫码登录、在另一台设备上点确认 |
| 人机验证 | 图形验证码、滑块、点选。不绕过 |
| 钱 | 付款确认、银行卡验证、支付密码。Bot 可以把购物车和订单填好，最后一下由人点 |
| 身份核验 | 实名、人脸、上传证件 |
| 明确要求真人 | 网站声明需要本人操作，签署协议 |
| 卡住 | 连续 3 个动作后画面没有变化；同一步用不同办法失败 3 次；出现看不懂的系统对话框 |

到了某个网站的登录页，先查有没有对应的连接器。有就发「连接 XX」卡片，连好以后不用再接管；没有才请求接管。

交还的约定：用户点「我完成了」后，Bot 先截一张图确认到了预期的状态（例如已经登录）。没到就说明看到了什么并再请一次，最多两次。用户点「我做不了」时，Bot 给出别的办法或者停下，不重试同一步。

本机上「接管」的含义相反：电脑本来就是用户的，Bot 是借用。所以没有接管卡片，用户随时动手，Bot 自动让位（§3.5）。本机上遇到上表的情况，Bot 发一张普通的提问卡：「请在你的电脑上完成登录，然后点继续」。

### 4.4 什么时候确认

| 动作 | 默认 | 卡片上的警示 |
|---|---|---|
| 对外发消息、邮件、邀请 | 先问 | 会把内容发到对话之外 |
| 发布内容（公众号、社交平台、网站上线） | 先问 | 公开可见 |
| 删除或覆盖工作区以外的数据，或无法恢复的数据 | 先问 | 这一步无法撤销 |
| 改权限、登录或安全设置 | 先问 | 会改登录或安全设置 |
| 改生产环境 | 先问 | 影响线上 |
| 接受法律条款 | 先问 | — |
| 把文件上传到第三方网站 | 先问 | 会把数据分享到对话之外 |
| 本机命令，云和本机之间搬文件 | 先问（§3.5） | 显示完整命令或文件清单 |
| 购买、转账 | 不走确认，走接管 | — |

判断一个动作是否属于上表，分三层，前两层是确定性的：

1. **按工具。** 连接器的发送类操作、`execute` 里匹配到的危险命令（删工作区以外的路径、`git push`、发布命令）、生成分享链接，直接拦。
2. **按要点的控件。** `cloud_computer` 点击之前，读无障碍树里光标下那个控件的名字。名字含「发送、提交、发布、支付、购买、下单、删除、确认订单」或对应英文时，这次点击先变成确认卡。成本是一次无障碍查询。
3. **模型自己申报。** 系统提示要求在上表动作前调用 `request_approval`。这一层会漏，所以放最后。

独立的审查模型（Grok 的做法）放到 §12 的 T5，等前两层的漏拦和误拦数据出来再决定。

规则按 Bot 保存，分「自动允许」和「先问」，冲突时「先问」优先，各不超过 20 条。新建的「自动允许」先进观察期：三次都只记录「本来会自动允许」，仍然发确认卡；用户看过记录再转正。这是从 Super-agent 的 observe → auto 借来的。

### 4.5 没人在场

| | 对话里发起，用户在 | 定时、IM 发起，或用户已离开 |
|---|---|---|
| 提问 | 发卡片 | 不问，按假设做并记下来 |
| 确认 | 发卡片，不过期 | 任务挂起为「等你」，推送，24 小时后过期 |
| 接管 | 发卡片并放大浮窗，不过期 | 同上；云电脑按空闲规则暂停，暂停期间只收磁盘费。用户点开卡片时恢复（约 5 秒），Bot 重新走到那一步 |
| 过期以后 | — | 这次运行记为「需要你处理，已过期」，附最后一帧画面。下一次定时照常执行 |
| 上一次还在等 | — | 新的一次跳过，记一条「上一次还在等你」 |
| 连续两次都要接管 | — | 建议接连接器，或暂停这条定时任务，由用户选 |

有效期从 Grok 的 30 分钟改成 24 小时，是因为暂停的电脑几乎不花钱，而凌晨的定时任务等不到 30 分钟内有人处理。见 §13 Q3。

卡片记录存数据库（`bot_handoffs`），重启不丢。过期时 Bot 收到明确的超时结果。这修掉 §1 的缺口 4 和 5。

群聊里只有账号主人能确认和接管。IM 群里其他人的消息可以提出请求，但不带任何授权；他们触发的有后果动作，确认卡发给主人。

### 4.6 接管时的隐私

- 接管期间不向模型发任何截图，Bot 的命令和操作被拒（已有）。
- 交还后的第一张截图，先用无障碍树找到密码框并打码。
- 用户在接管时输入的内容不进对话记录，不进模型上下文。
- 接管过程默认不录屏。「教 Bot 做一遍」是用户另外主动打开的功能。

## 5. 任务执行质量

### 5.1 质量差在哪

| 问题 | 表现 | 对策 |
|---|---|---|
| 没听懂 | 做了一件相近但不是用户要的事 | 契约里先复述目标和验收条件（§5.2） |
| 半途而止 | 做了一半就说完成 | 完成要过校验（§5.4） |
| 说做了其实没做 | 文件不存在、打不开、内容是占位符 | 证据和交付前检查（§5.4、§6.3） |
| 卡住空转 | 反复截图、反复重试，积分一直在走 | 看门狗（§5.5） |
| 长任务忘事 | 压缩上下文以后丢了要求 | 任务记录在上下文之外（§5.6） |
| 报喜不报忧 | 没做的部分不提 | 交付单的固定结构（§6.4） |

### 5.2 任务契约

Bot 判断这是一件「任务」而不是一句问答时，先调用 `task_plan` 写下：

| 字段 | 内容 |
|---|---|
| 目标 | 一句话，用用户的话 |
| 验收条件 | 2–5 条，每条都能检查。例如「表格包含三家公司 2026 年 Q3 的价格，币种统一为人民币」 |
| 步骤 | 沿用现有的 `write_todos` |
| 执行位置 | §3.4 的结果 |
| 假设 | 没问用户、自己定的事 |
| 预算 | 时长上限（§5.5） |

数据模型复用群聊 Goal（`Goal{criteria, stages[{status, evidence}], status}`），并沿用它的校验：完成的阶段必须有证据。私聊任务相当于只有一个成员的 Goal，由 Bot 起草，不需要用户填表。

### 5.3 三档投入

| 档位 | 什么时候 | 做什么 | 界面 |
|---|---|---|---|
| 直接回答 | 问答、小改动、一步就完的事 | 不建任务 | 只有消息 |
| 标准任务 | 用到电脑，或者要产出文件 | 契约、执行、自检、交付单 | 任务卡 |
| 深度任务 | 预计超过 15 分钟，或有无法撤销的产出，或用户选了「深度」 | 再加：开头集中提问、独立复核（§5.4）、分段存档 | 任务卡，计划先给用户看一眼 |

档位由模型按上表选，显示在任务卡上，用户可以改。

### 5.4 用证据验收

每条验收条件要有下面某一种证据才能标为通过：

| 证据 | 例子 |
|---|---|
| 命令输出 | 测试通过；`wc -l` 的行数；接口返回 200 |
| 文件检查 | 文档转成 PDF 后有 12 页；表格有 3 个工作表、公式已重算 |
| 截图 | 网页上显示「发布成功」 |
| 数据核对 | 汇总行数等于各来源行数之和 |
| 外部回执 | 邮件的消息 ID；日程的链接 |

`task_finish` 是一道确定性的关卡：任何一条验收条件没有状态（通过、未通过、跳过并写明原因）或没有证据，调用被拒，Bot 必须补上。有未通过或跳过的条件时，任务状态是「部分完成」，不是「已完成」。

深度任务再加一次独立复核：一个新开的子 Agent 只拿到原始需求、验收条件、产物和证据，拿不到执行过程中的推理，给出通过或问题清单。最多改两轮，仍有问题就如实写进交付单。群聊 Goal 里管理员的复核是同一个模式。复核会多花模型积分，具体比例上线后实测；默认开还是按需开见 §13 Q4。

### 5.5 看门狗

一个不调用模型的监视器，跟着每个运行中的任务：

| 监视 | 条件 | 动作 |
|---|---|---|
| 画面不变 | 连续 3 次操作后截图哈希相同 | 提醒 Bot 换办法（先看无障碍树、改用命令）。提醒两次仍不变 → 请求接管 |
| 重复调用 | 同一工具同一参数连续 5 次（`cloud_computer`；其他工具维持现有上限） | 结束这一步并要求换办法 |
| 同一错误 | 同一个错误出现 3 次 | 禁止再用同一办法，Bot 换路或者如实停下 |
| 预算 | 时长用到 80% | 任务卡提示 |
| 预算 | 用到 100% | 暂停并问「再给多少」。没人在场则停止并报告 |
| 没动静 | 任务标着运行中，但 120 秒没有任何工具调用或输出 | 自动续一次；再次发生则标为中断并通知 |
| 模型或网络出错 | 临时性错误 | 退避重试 3 次 |
| 服务重启 | — | 从检查点继续，任务卡显示「已从中断处继续」 |

所有动作都写进任务事件，任务卡展开后能看到。阈值集中在一个配置里，§11 的评测用它们调参。

### 5.6 长任务不忘事

- 任务记录（契约、进度、关键发现）存在数据库里，同时写到工作区的 `.octop/tasks/<任务 id>/task.md`。上下文压缩之后，把记录重新放进上下文。
- 大段的命令输出只留末尾约 4000 字在上下文里，全文落到工作区文件，上下文里给路径。
- 深度任务每完成一步存一次档，可以从任意一步「从这里重做」。

### 5.7 衡量

| 指标 | 含义 | 目标方向 |
|---|---|---|
| 假完成数 | 宣布完成但复核或用户发现没完成 | 必须为 0 |
| 验收通过率 | 通过的验收条件 / 全部 | 高 |
| 一次通过率 | 用户没有要求重做或返工 | 高 |
| 每任务人工次数 | 提问、确认、接管之和 | 低，但该接管的不能少 |
| 卡住率 | 触发看门狗的任务占比 | 低 |
| 每任务花费和时长 | 积分、分钟、步数 | 低 |
| 产物打开失败率 | 交付前检查未通过 | 0 |

这些指标从 `bot_tasks` 和 `bot_task_events` 算出，先给运营方看，不对用户展示。

## 6. 交付产物

### 6.1 什么算产物

| 类型 | 例子 | 卡片预览 |
|---|---|---|
| 文档 | docx、pdf、md | 第一页缩略图、页数 |
| 表格 | xlsx、csv | 前几行、工作表数和行数 |
| 演示 | pptx | 前三页横排缩略图、页数 |
| 图片和视频 | png、jpg、mp4 | 缩略图、时长 |
| 代码和项目 | zip、改动摘要 | 文件数、怎么运行 |
| 网页和应用 | HTML、本地站点 | 截图、「在云电脑里打开」 |
| 回执 | 已发送的邮件、已建的日程、已发布的文章 | 对象、时间、链接 |

回执也是产物：Bot 在外面做了有后果的事，用户要有一张能点回去核对的卡片。

### 6.2 规则

- **显式交付。** Bot 调用 `publish_file(path, title, note)` 才算交付。没有交付的文件留在工作区，不出现在对话里。
- **短的直接写在消息里，长的出文件。** 超过一屏的内容，或有结构的内容（表格、多章节），出文件。
- **版本。** 同一个对话里再次交付同名文件算新版本。原卡片原地更新成 v2，旧版本仍可下载。
- **命名。** 文件名要说人话，例如 `竞品价格对比_2026Q3.xlsx`，不要 `output.xlsx`。交付前检查会拦 `output`、`untitled`、`新建` 这类名字。
- **存放。** 沿用 cloud-plan §9：上传对象存储，客户端只拿签名链接。本机用法下产物就是工作目录里的文件。

### 6.3 交付前检查

`publish_file` 在服务端自动做这些检查，不经过模型。不通过就拒绝交付，把原因还给 Bot：

| 检查 | 方法 |
|---|---|
| 存在且非空 | 文件大小 |
| 能打开 | Office 文档用 LibreOffice 无界面转 PDF；图片解码；PDF 读页数；zip 校验；CSV 解析 |
| 有实际内容 | 页数或行数大于 0；没有只剩模板占位符的页 |
| 中文正常 | 渲染出的缩略图里没有成片的方块字（云电脑镜像预装中文字体，这里做回归） |
| 代码能跑 | 项目里有测试或构建命令时，由 Bot 运行并把输出作为证据 |
| 网页正常 | 在云电脑的 Chrome 里加载，没有控制台报错，截一张图 |

转 PDF 和截图得到的缩略图直接用作卡片预览。检查结果存在产物记录里，卡片上显示成一行「已检查：能打开 · 12 页」。

### 6.4 交付单

任务结束时的最后一条消息，结构固定：

```
✓ 已完成：三家竞品 2026 年 Q3 价格对比表                    （或「部分完成」「未完成」）

产物
  [竞品价格对比_2026Q3.xlsx  v1 · 3 个工作表 · 已检查]

验收
  ✓ 包含 A、B、C 三家的 Q3 价格          证据：表格 42 行，来源链接在「来源」表
  ✓ 币种统一为人民币                      证据：汇率取 11-24 中间价，见「说明」表
  ✗ 包含各家的折扣政策                    C 家官网没有公开折扣，未填

我自己定的
  价格取官网标价，不含税。

用时 8 分钟 · 云电脑 6 分钟 · 51 积分
```

有未通过的验收条件时，第一行不能写「已完成」。结尾最多一句下一步建议，不罗列。

### 6.5 对产物能做什么

预览、下载、让 Bot 修改（把产物引用进输入框）、发到群里或转给另一个 Bot、在云电脑里打开、存到本机文件夹（桌面，需要本机连接）、生成分享链接（cloud-plan §9.2，后做）。

每个对话和每个 Bot 的资料页有一个「产物」页，按任务分组列出全部交付过的东西。

## 7. 界面与交互

### 7.1 原则

现在的 Bot 对话不显示工具步骤，只在底部用一行状态说明 Bot 在做什么（`BotTurnView.tsx`、`BotWorkingLine.tsx`）。这个克制要保留。新增的东西遵守三条：

1. 一个任务一张卡，卡片原地更新，不往下刷屏。
2. 需要用户的事最显眼，其他都安静。
3. 用户随时能看到三个事实：Bot 在哪做、做到哪了、花了多少。

### 7.2 任务卡

标准和深度任务用任务卡取代底部那行状态。直接回答仍然用原来那一行。

```
┌────────────────────────────────────────────────────────────┐
│ ◐ 整理 Q3 竞品价格表                      云电脑 · 6 分钟 · 38 积分 │
│ ━━━━━━━━━━━━━━━━━━━━░░░░░░░░░░  3 / 5                              │
│ ✓ 打开三家官网收集价格                                             │
│ ✓ 汇总成表格                                                       │
│ ◐ 核对币种和单位                                                   │
│ ○ 生成图表                                                         │
│ ○ 检查并交付                                                       │
│ 验收条件 3 条 ▸                                  [看画面]  [停止]   │
└────────────────────────────────────────────────────────────┘
```

| 状态 | 卡片 | 可以做的事 |
|---|---|---|
| 计划中 | 只有标题和骨架 | 停止 |
| 等你确认计划（仅深度任务） | 完整计划和验收条件 | 开始、修改、取消 |
| 进行中 | 如上图，当前步骤有流光 | 看画面、停止、发消息改方向 |
| 等你 | 左边线变琥珀色，标题下一行写原因，下方出现对应的「需要你」卡 | 处理那张卡 |
| 检查中 | 步骤全部打勾，显示「正在核对验收条件」 | 停止 |
| 已完成 / 部分完成 | 收成一行：`✓ 已完成 · 5 步 · 8 分钟 · 51 积分 ▸`，下面是交付单和产物卡 | 展开看步骤、证据和看门狗记录 |
| 已停止 / 出错 | 收成一行并写原因 | 继续、重做 |

位置标签（「云电脑」「这台电脑」「不用电脑」）在右上角。中途换位置时标签更新，步骤列表里插一行灰字说明，例如「改到这台电脑：需要读取桌面上的合同」。

「看画面」展开已有的云电脑浮窗（cloud-plan §12.7），浮窗顶栏显示任务卡的当前步骤。

### 7.3 「需要你」卡片族

三种卡片外形一致：琥珀色左边线，Bot 头像，一句原因，最多三个按钮。

| 卡片 | 内容 | 按钮 |
|---|---|---|
| 提问（已有 `BotAskCard`） | 最多三个问题 | 选项，或自己填 |
| 确认（新） | 要做什么、对象是谁、完整的命令或内容预览、警示标签 | 允许一次（主）、总是允许、拒绝 |
| 接管（已有，补强） | 原因、卡住那一刻的缩略图 | 接管云电脑（主）、我做不了。接管中变成「你在操作 · 02:13」和「我完成了」 |

交互细节：

- 卡片出现时不抢输入焦点，读屏会播报一次。
- 确认卡没有默认按钮，回车不会触发「允许」。Esc 等于拒绝。
- 用户直接在输入框回一句话也算回答：「可以」算允许一次，其余内容算拒绝并把这句话交给 Bot。
- 卡片处理完以后收成一行记录，例如「你允许了：发送邮件给 zhang@…」。

### 7.4 汇总和通知

- 通讯录里，有事等用户的 Bot 排到最前，头像带琥珀色点。
- 标题栏有一个「待办」入口，列出所有 Bot 的「需要你」卡片，可以直接在里面处理。
- 桌面悬浮球变琥珀色。
- 桌面客户端在用时，通知只发到桌面。卡片 3 分钟没人处理再推到手机。
- 推送只带 Bot 名字和类别（需要你确认 / 需要你接管 / 任务完成 / 余额不足），不带内容。

### 7.5 产物卡

```
┌──────────┬──────────────────────────────────────────┐
│          │ 竞品价格对比_2026Q3.xlsx              v2  │
│  缩略图  │ 表格 · 3 个工作表 · 48 KB                 │
│          │ 已检查：能打开 · 42 行                    │
│          │ [预览]  [下载]  [让 Bot 修改]  ···        │
└──────────┴──────────────────────────────────────────┘
```

多个产物横向排列，超过三个时折叠成「另外 N 个」。回执卡没有缩略图，用一个图标加对象和时间。

### 7.6 输入框

- 「在哪做」标签：只在两个位置都可用时出现，默认「自动」。
- 「深度」开关：收在输入框的「＋」菜单里，不占主界面。
- 任务进行中发消息默认是「改方向」，Bot 在当前步骤结束后读到。按住 Shift 发送是「排在后面」，等这个任务完成再处理。

### 7.7 Bot 资料「电脑」一栏

| 用法 | 显示 |
|---|---|
| 本机 | 现有的应用授权面板 |
| 灵策，没有本机连接 | 云电脑卡片 |
| 灵策，有本机连接 | 上面是云电脑卡片；下面是「这台电脑」：设备名、在线状态、策略、授权文件夹、授权应用；最上方是「执行位置」选择 |

### 7.8 群聊

- 群 Goal 的每个阶段对应一张紧凑的任务行：成员头像、阶段名、位置标签、进度。点开是完整任务卡。
- 「需要你」卡片出现在群里，同时进待办。只有账号主人能处理。

### 7.9 手机

- 同一套卡片。任务卡默认两行（标题加当前步骤），点开看全部步骤。
- 实时活动和常驻通知显示任务卡的内容：当前步骤、几分之几、用时、积分、停止（cloud-plan §12.5.5）。
- 接管从推送直接进全屏画面。
- 手机不显示「这台电脑」的策略编辑，只显示状态，可以一键改成「永不允许」。

### 7.10 空状态和出错

| 情况 | 显示 |
|---|---|
| 云电脑启动中 | 浮窗和任务卡显示「电脑启动中，约 5 秒」，带骨架屏 |
| 余额不足 | 现有的积分不足卡片，任务卡停在「等你」 |
| 本机离线 | 「这台电脑不在线。打开桌面客户端后继续」，带「改用云电脑」（如果这一步可以） |
| 检查没通过 | 用户看不到，Bot 自己修。修两次仍不通过，才在交付单里写出来 |
| Bot 说做不了 | 普通消息，写明原因和它试过什么，不是红色报错 |

### 7.11 无障碍

- 任务卡是 `role="status"`，步骤变化用 `aria-live="polite"` 播报，每 5 秒最多一次。
- 状态不只靠颜色：每个状态有图标和文字。
- 所有卡片能用键盘走完。
- 系统开了「减少动态效果」时按 §8.4 处理。

## 8. 动效

### 8.1 原则

1. 动效只表达状态：谁在操作（Bot 还是你）、进展到哪、是否需要你。没有纯装饰的动画。
2. 一个对话里同时只有一个持续运动的元素。优先级：浮窗光边 > 任务卡当前步骤的流光 > 头像动画。高优先级的在动时，低优先级的静止。
3. 进入比离开稍慢，都不超过 320 毫秒。循环动画的周期不短于 1.6 秒。
4. 动画不阻塞操作：进行中可以点击，可以被新状态打断。
5. 完成时不放烟花。一个对勾画完，卡片收起。

### 8.2 令牌

沿用现有样式里的取值（过渡 0.12–0.2 秒，`pulse` 1.6 秒，`workingShimmer` 2.2 秒，`breathe` 2.4 秒），收成变量：

| 令牌 | 值 | 用途 |
|---|---|---|
| `--motion-fast` | 120ms | 悬停、按下 |
| `--motion-base` | 200ms | 出现、状态变化、颜色过渡 |
| `--motion-slow` | 320ms | 展开收起、浮窗改大小 |
| `--motion-shimmer` | 2200ms 线性 | 当前步骤的流光 |
| `--motion-breath` | 2400ms | 呼吸点、光边 |
| `--ease-standard` | `cubic-bezier(0.2, 0, 0, 1)` | 默认 |
| `--ease-exit` | `cubic-bezier(0.4, 0, 1, 1)` | 离开 |
| `--ease-snap` | `cubic-bezier(0.34, 1.56, 0.64, 1)` | 只用于浮窗吸附到角落 |

### 8.3 逐个组件

| 组件 | 时机 | 动效 |
|---|---|---|
| 任务卡 | 出现 | 淡入并上移 8px，200ms。步骤逐行出现，每行间隔 30ms，最多 5 行 |
| 任务卡 | 一步完成 | 圆圈画成对勾（描边 180ms），这一行文字变淡 200ms，进度条变宽 320ms，80ms 后下一步开始流光 |
| 任务卡 | 进入「等你」 | 左边线 200ms 过渡到琥珀色，整卡轻微放大一次（1 → 1.02 → 1，400ms），不循环 |
| 任务卡 | 完成 | 高度 320ms 收成一行，对勾画一次 |
| 任务卡 | 出错或停止 | 只换颜色和图标，不抖动 |
| 位置标签 | 换位置 | 旧标签淡出、新标签淡入，共 200ms |
| 「需要你」卡 | 出现 | 淡入并上移 8px，200ms。通讯录上的琥珀点按 2400ms 呼吸，处理后停止 |
| 「需要你」卡 | 处理完 | 320ms 收成一行记录 |
| 浮窗 | Bot 在操作 | 2px 品牌色光边，2400ms 呼吸（已有） |
| 浮窗 | Bot 点击 | 画面上点击的位置出现一个扩散的圆环，240ms。需要状态接口的 `activity` 带上坐标 |
| 浮窗 | 你接管 | 光边 200ms 变成蓝色实线，顶栏文字换成「你在操作」 |
| 浮窗 | 交还 | 蓝色光边沿边框扫一圈回到品牌色，600ms |
| 浮窗 | 电脑启动 | 骨架屏带斜向流光，第一帧到达时 200ms 交叉淡入 |
| 产物卡 | 出现 | 0.96 → 1 缩放并淡入，240ms。缩略图由模糊到清晰 200ms。检查项逐个打勾，间隔 60ms |
| 产物卡 | 出新版本 | 缩略图 200ms 交叉淡入，版本角标弹一下 |
| 头像 | 各状态 | 沿用现有四个动画：计划时 `think`，操作电脑时 `scan`，等用户时 `look`，完成时 `nod` 一次 |

手机上时长相同，再加触感：出现「需要你」是一次轻触感，交付完成是一次成功触感。

### 8.4 减少动态效果和性能

- 系统开了「减少动态效果」：位移和缩放全部去掉，只留 120ms 的透明度变化。流光、呼吸、圆环关掉，改用静态图标和文字。
- 只对 `transform` 和 `opacity` 做动画。
- 标签页不可见或元素滚出视口时，停掉循环动画。
- 同一时间只连一路实时画面（已有约定）。

## 9. 和 DeepSeek Super-agent 结合

### 9.1 它是什么

来自官方仓库 [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（2026-11-24 读取）：

- MIT 许可，TypeScript。仓库只有 2026-10-31 的一次提交。README 写明是研究原型，不是官方产品，和内部版本不完全相同。
- 是 DeepSeek Harness 的插件，离开它不能运行。
- 入口是一个 GitHub 仓库加可选的飞书群。常驻的 Router 对每条请求做四选一：接受、并入已有任务、停止、忽略。接受后为每个任务（Ticket）开一个独立的 Worker 会话和工作目录。
- 请求先过确定性的关卡（发件人白名单、准入表），再由模型逐条评估规则。
- 已订阅某个话题的任务，该话题的后续消息直接送给对应的 Worker，不经 Router。
- Worker 并发有上限，另留一个名额给人的消息。
- 回复经发件箱发送，带回执，失败后按 5 秒到 300 秒退避重试。
- 自动接受有三档：关、观察、自动。建议先观察再转自动。
- Worker 以运维者的系统用户身份直接跑命令，没有沙箱，没有审批。
- 读到的官方文档里没有计划、自检和验收环节，也没有看门狗和外部记忆。这几项出现在二手报道和第三方重写版（LofiSu/dsh-super-agent）里，不能当作官方设计。官方文档有几篇没读到（理念、提示词、面板、部署、示例），结论以这个范围为限。

### 9.2 结论

不直接集成代码，原因有三：语言不同且绑定 DeepSeek Harness；它是单租户设计，执行环境没有隔离，我们是多租户加云电脑；它不解决单个任务的质量。

它的调度设计值得借，而且正好是我们薄弱的地方。Chief 和群聊现在靠 @ 接力，没有「任务」这个对象。

### 9.3 借什么

| Super-agent | Octop Bot 里对应 | 怎么用 |
|---|---|---|
| Router 四选一：接受、并入、停止、忽略 | Chief、群管理员 | Chief 收到请求时先判断：开新任务、并入进行中的任务、停掉某个任务、不处理。现在每句话都是一次新的接力 |
| 关卡加评估 | §3.4 的硬规则加模型选择；§4.4 的三层判断 | 已采用：确定性的先做，模型后做 |
| Ticket 和它的阶段（含等人的阶段） | `bot_tasks` 和「等你」状态 | 已采用 |
| 每个任务独立会话和目录 | 任务用独立的线程和 `tasks/<id>/` 目录 | 长任务不污染私聊上下文，做完只把交付单带回主对话 |
| 订阅直通 | 任务线程里的后续消息直接给负责的 Bot | 群里追问不必每次经过管理员。二手报道里，去掉直通后 Router 的决策多了约 30% |
| 并发名额加给人预留的名额 | 每个用户的并发任务上限 | 定时任务占满名额时，用户发的消息仍然立刻有 Bot 响应 |
| 发件箱、回执、退避重试 | IM 回复和手机推送 | 「需要你」和「已完成」的通知不能丢 |
| 观察 → 自动 | 审批规则的观察期（§4.4）；IM 群里自动接活 | 新的自动化先只记录不执行，看过再放开 |
| 没有沙箱和审批 | — | 不借。这里我们的设计更强 |

成本提醒：二手报道里，合成负载下 Router 加 Worker 的读缓存 token 约为单会话的 3.8 倍（2323 万对 605 万）。所以调度层只放在请求会并发到达的地方（群聊、IM、Chief 分派），私聊直接由 Bot 自己处理。

这一层排在 §12 的 T5，是否进入范围见 §13 Q6。

已验证：`tests/unit/bot_tasks/`（契约、结束关卡、修订、过期、看门狗）、`test_octop_bot_workspace.py` 的挂载检查、前端 `botTasks.test.ts` 和 `BotTaskCard.test.tsx`；任务卡和交付单在浏览器里看过桌面宽度和手机宽度。

### 12.3 T2 完成情况（2026-11-24）

分支 `feature/bot-t1-task-quality`，接在 T1 之后。已有的文件卡片（网页、iOS、Android 的 Grok 式卡片，PDF 首页和 CSV 预览）和 Bot 资料里的「资料库」（这个 Bot 发过的文件，按今天、本周、更早分组）沿用，不再另做 `publish_file` 工具和「产物」页：Bot 仍用 `send_file_to_user` 交付，T2 在它外面加检查和记录。

| 部分 | 做了什么 | 位置 |
|---|---|---|
| 交付前检查 | `send_file_to_user` 的结果交给用户之前，读取实际文件（云电脑上的文件已由 harness 取到服务器本地）做检查，不调用模型：不能为空；PDF、Office、图片、压缩包、JSON 要能打开；Word 要有正文，Excel 要有单元格，PPT 要有幻灯片，CSV 要有表头以外的数据行；正文里不能留模板文字（lorem ipsum、`{{ 变量 }}`、「在此输入」等）；文件名不能是 output、untitled、未命名、新建这类。不合格就不发，把原因退给模型改了重发。超过 50 MB 只查文件名 | `infra/bot_tasks/deliverables.py`、`watchdog.py` `_deliver` |
| 检查结果 | 以数据返回（页数、数据行数、工作表数、幻灯片数、字数、行数、文件数、图片尺寸），由前端按用户语言显示 | `inspect_file` 的 `facts` |
| 记到任务上 | 任务运行中交付的文件记进任务（文件名、路径、大小、检查结果、时间）；同名文件再次交付记为新版本 | `model.py` `Deliverable` |
| 交付单 | 新增「产物」一节：类型图标、文件名、版本角标（v2 起）、大小、「已检查：3 个工作表」；同名文件只显示最新版本 | `BotTaskReport` |
| 系统提示 | 写清楚：写好文件不等于交付，要用 `send_file_to_user`；交付前会被检查 | `BRIEFING` 第 4 条 |

已验证：`tests/unit/bot_tasks/test_deliverables.py`（命名、空文件、损坏文件、只有表头、空工作簿、模板文字、检查结果）、`test_task_watchdog.py`（不合格的文件不发、合格的记进任务并带版本）、前端交付单测试；`make all` 通过（6357 passed）。

没有做：

- 用 LibreOffice 把 Office 文档转成 PDF 再检查、渲染缩略图检查中文字体，没做。现在只检查文件结构和内容。
- 代码项目「能跑」、网页「能打开且没有报错」这类检查，仍然靠 T1 的验收证据，没有放进交付前检查。
- 用真实模型验证交付检查：本机这个文件夹的开发服务器数量已到上限（其他会话占了 5 个），这次没跑。

### 12.4 T3 完成情况（2026-11-24）

分支 `feature/bot-t1-task-quality`，接在 T2 之后。

| 部分 | 做了什么 | 位置 |
|---|---|---|
| 确认卡 | 新工具 `request_approval(category, target, detail, irreversible)`：发送、发布、提交、删除或覆盖、改权限、改线上系统、接受条款、上传到外部网站之前调用。付款不走确认，走接管。卡片用现有的提问卡（三端都能显示，定时任务里会按 T0 挂起），选项是允许一次、总是允许、拒绝；用户在输入框写别的话也算拒绝，并把原话转给 Bot | `infra/bot_tasks/approvals.py` |
| 总是允许 | 按 Bot 记住「这一类动作 + 这个对象」（例如发给这个邮箱），下次同样的就不再问，换一个对象照常问。每个 Bot 最多 40 条，存在 settings | `ApprovalRules` |
| 点击前预检 | `cloud_computer` 点击（单击、双击）前读无障碍树，找到点中的那个控件：名字像「发送、回复、提交、发布、分享到、删除、清空」或对应英文的，先发确认卡（只有允许一次和拒绝）；名字像「支付、付款、购买、下单、结算、Pay、Buy、Checkout」的直接拒绝，要求请用户接管。读不到无障碍树时照常点击 | `computer_use.py` `guard_click`、`control_at` |
| 交还后核对 | 用户交还电脑后，Bot 先截图确认那一步真的完成（例如已经登录），没完成就说明看到了什么并再请一次接管，再两次还不行就停下来说明原因 | `request_takeover` 的返回 |
| 待办汇总 | `GET /api/octop-bot/inbox`：当前用户所有 Bot 正在等的提问、确认、接管（以及工具审批），最新的在前，标出来自定时任务的。网页每 15 秒刷新一次（页面在前台时），回到页面时立刻刷新 | `infra/bot_tasks/inbox.py`、`api/routers/bot_inbox.py`、`useBotInbox.ts` |
| 通讯录提示 | 有事等你的 Bot 在通讯录里多一个琥珀色呼吸点，副标题变成「等你处理」 | `DirectoryItem.tsx` |
| 网页确认卡 | 还在等的确认显示成专门的确认卡：琥珀色左边线、三个同样大小的按钮、没有默认选项（回车不会确认），Esc 等于拒绝。回答之后照常显示成提问卡的记录 | `BotApprovalCard.tsx` |
| 系统提示 | 任务说明和云电脑说明都改成：有后果的动作调用 `request_approval`，付款一律 `request_takeover` | `BRIEFING`、`ComputerBriefing` |

已验证：`tests/unit/bot_tasks/test_approvals.py`（三种回答、总是允许只对同类同对象生效、其他回答算拒绝）、`test_computer_use.py`（控件定位、点「发送」先问、点「立即支付」不点、普通按钮直接点、交还后核对）、`test_octop_bot_workspace.py`（待办只列自己的、分类正确）、前端确认卡和通讯录提示测试。

没有做：

- 手机推送（TPNS）和「桌面在用时 3 分钟后才推到手机」：推送通道还没有。现在网页会弹通知（定时任务挂起时），通讯录有琥珀点。
- 待办记录仍在服务进程内存里，重启后清空，卡片也不能再回答。
- 交还后的第一张截图给密码框打码：没做。
- 「总是允许」的观察期（先记录三次再生效）、独立的审查模型：没做。
- 点击预检每次点击多读一次无障碍树，会让每一步慢一些；还没有在真实云电脑上量过多慢。
- 手机端：确认卡显示成普通提问卡（能用，但没有专门样式），没有待办汇总。

# Octop Bot 两套账号：本地 Octop 账号 与 灵策智算账号（设计稿，2026-11-25；§6 已由用户确认）

用户 11-25 定了方向，选的是方案 C「本机运行 + 云端同步」。这份文档替换 `octop-bot-cloud-plan.md` §12.4 里桌面端的部分：那一节写的是「去掉 Octop 密码、本机用法免登录」和 11-24 的方案 B「登录灵策就把数据搬到 bot.lynxce.cn，桌面变成云端的客户端」。网页、手机和自建服务器的部分不变。

## 0. 第一原则

> 灵策智算账号负责云端协同；本地 Octop 账号负责隐私隔离。

| | 本地 Octop 账号 | 灵策智算账号 |
|---|---|---|
| 作用 | 隐私隔离：数据只在这台电脑上，不上云，也不经过灵策 | 云端协同：多端同步，手机和网页上可以接着聊，团队和群组协作，用灵策的模型和积分 |
| 怎么来 | 第一次打开桌面客户端时，像上游 Octop 一样设置管理员账号、密码和模型 | 灵策手机号或邮箱验证码、密码、WorkBuddy 登录，没有账号就自动注册 |
| Bot 在哪跑 | 本机 Octop | 在本机发的消息由本机 Octop 跑；在手机或网页发的消息由云端 Octop（bot.lynxce.cn）跑 |
| 模型和计费 | 自己配：厂商 API Key（腾讯云、百炼、方舟……）或本地模型（Ollama、LM Studio），不走灵策 | 灵策模型扣灵策积分；也可以用「我的 API Key」，由厂商收费 |
| Bot 的电脑 | 这台电脑（授权给 Bot 的本机应用） | 本机发的消息用这台电脑；云端发的消息用云电脑（CVM / AGS），按分钟扣积分 |

**边界**：灵策账号是挂在本地账号上的一个「可选连接」，不是另一套数据。本地账号永远是这台电脑上数据的主人；登录灵策后，只有用户标成「协同」的 Bot 才会上云。

## 1. 两套账号的关系

### 1.1 本地 Octop 账号
- 首次启动（全新安装）恢复上游 Octop 的做法，也就是 §12.4 之前的样子：
  1. 设置显示名和密码（密码至少 8 位，本机存哈希）。登录用户名第 1 期固定为 `local`，不让用户改：`setup.py` 的 `LOCAL_DESKTOP_USERNAME`、`auth_lynxce.py` 的 `LEGACY_OWNER_USERNAME` 都按这个名字认人。从局域网或别的设备登录时，用户名填 `local`。
  2. 配置模型，三选一：「我的 API Key」「本地模型」「登录灵策智算」。选了灵策，就进入 §1.2 的绑定流程。
- 设好以后，日常打开**不用再输密码**：沿用现在的设备凭据（`/api/auth/device/*`，壳把凭据存在钥匙串里）自动登录。下面几种情况才要输密码：设备凭据失效；改密码（上游本来就要输旧密码）；从局域网或别的设备访问这台电脑上的 Octop（上游的多用户和远程访问场景）。「改其他安全设置前再输一次密码」以后单独排期，不放在第 1、2 期。
- 一台电脑可以有多个本地账号（上游本来就是多用户）。每个本地账号各自绑定自己的灵策账号，数据互相隔离。
- **已经装过的用户**：现在本机用法用的是 `local` 账号加设备凭据，没有用户知道的密码。升级后第一次打开时提示「为这台电脑设置一个密码」，这一步可以跳过，但会一直提醒。数据不用迁移。
- **补设密码的实现**：
  - 不能用「password_hash 为空」来判断有没有设过密码。桌面的 `local` 管理员其实有一个服务端随机生成、没人知道的密码（见 `auth_device.py` 开头的注释）。
  - 用 settings 键 `octop_bot:local_password_set:<uid>` 做标记，没有这个键就是用户还没设过。
  - 接口 `POST /api/octop-bot/account/password`：只在桌面壳下可用，要求已登录，只在没有标记时允许，写入走 infra 里 UserManager 新加的 `set_initial_password`。新安装的首启页和老用户补设密码都走这个接口。
  - 设过之后改密码走上游的 `/api/auth/password`，要输旧密码。
  - 设密码会让 `password_version` 加 1，网页当前的 JWT 会立刻失效。所以这个接口要直接返回新的 access_token；设备凭据不受影响。

### 1.2 灵策账号挂在本地账号上
- 每个本地账号**同一时间最多绑一个**灵策账号。绑定关系保存在本机：沿用现在 `secret_repo` 里加密保存的会话 `lynxce.cloud.user.{uid}`（`infra/auth/lynxce_cloud.py`），和 `settings_repo` 里的模型 Key 归属 `octop_bot:lynxce:key_owner:{uid}`（`infra/agents/providers/lynxce.py`）。
- 绑定以后：
  - 模型默认用灵策（1.0.5 已做好：登录就签一把个人 Key，`CloudAccountModel`，扣灵策积分）；
  - 积分、充值和用量页显示这个灵策账号的数据；
  - 「协同」Bot 开始同步（§2）。
- **退出灵策**：协同 Bot 留在本机，变成「已断开」（还能在本机用，只是不再同步）；云端那份保持不动。重新登录同一个灵策账号就接着同步。
- **换另一个灵策账号**：和退出一样，先断开旧账号。旧账号的协同 Bot 在本机还是「已断开」，不会同步到新账号；新账号的协同 Bot 从云端拉下来。同一个 Bot 不会同时属于两个灵策账号。
- **只登录灵策、不设本地密码**是允许的，本地账号照样在后台建好，只是没有密码。这适合只想用灵策的人，和现在 1.0.5「选灵策智算」的体验一样。

### 1.3 一眼看出属于哪边
- Bot 头像右下角加小标：**🔒 本机**（不上云）、**☁ 协同**（同步到灵策云）、**⚠ 已断开**（协同 Bot 现在没有同步）。会话标题旁边、群聊成员列表里也显示同样的标记。
- Bot 资料页有一个「同步到灵策云」开关，旁边一行说明：「打开后，这个 Bot 的设置、对话和它发给你的文件会保存到灵策云，手机和网页可以接着聊；它在这台电脑上读过的文件、操作过的应用不会上传。」
- 手机和网页上只看得到协同 Bot。本机 Bot 在那里根本不存在，不是「看得到但不能聊」。
- 侧边栏可以按「本机 / 协同」筛选，账户菜单显示「灵策已连接 · 同步中 / 已暂停」。
- **存储**（2026-11-25 和桌面与 Web 对过）：
  - 存在 Agent 的 `config_json` 里：
    - `octop_bot.sync` 只存 `"local"` 或 `"cloud"`，没有这个键就当 local；
    - 设成 cloud 时同时写 `octop_bot.sync_account`，也就是当时绑定的灵策账号 id，和 key_owner 记的是同一个 account_id。
  - 「⚠ 已断开」不存，展示时计算：sync 为 cloud，并且当前本地账号没绑灵策、或者绑的账号 id 不等于 `sync_account`。这样退出、重新登录、换账号都不用改数据，重新登录同一个账号会自动恢复成 ☁。这个判断写在 infra 里的一个函数，各接口共用。
  - 接口返回的 `sync` 字段是三态：local、cloud、disconnected。
  - `PUT /api/octop-bot/bots/{id}/sync` 只接受 local 和 cloud；没绑灵策时设 cloud 返回 409。
  - 建 Bot 的接口、`octop_bot_create` 和 `create_team` 工具都接受可选的 sync，没传时绑了灵策就是 cloud，没绑就是 local。

## 2. 方案 C：同步怎么做

### 2.1 同步什么（只针对协同 Bot）

| 数据 | 同步 | 说明 |
|---|---|---|
| Bot 设置（名字、形象、人设/系统提示、所选模型、技能清单、连接器开关） | ✓ 双向 | 连接器的凭据**不**同步；云端没有的本机连接器在云端显示为「仅本机」 |
| 会话和消息（用户消息、Bot 最终回复、提问卡、附件卡） | ✓ 双向 | 工具调用的**原始输出不上云**，只同步一句摘要，例如「读取了 report.xlsx」。云端的模型上下文用回复和摘要 |
| Bot 发出的文件、用户上传的附件 | ✓ 双向 | 只同步消息里引用到的文件，走对象存储，按现在云端租户的 `octop-bot/` 前缀 |
| Bot 的整个工作区 | ✗（第三期可选） | 工作区里可能有从本机复制进来的文件 |
| 记忆（长期记忆） | ✓ 双向（第三期） | 由用户单独确认：「记忆也同步」默认打开，可以关掉。关掉后两边各记各的 |
| 群组（成员、时间线、Goal、阶段） | ✓（成员全是协同 Bot 的群才同步） | 群里只要有一个本机 Bot，整个群就留在本机，群头显示 🔒 |
| 团队笔记、侧边栏分组 | ✓ | |
| 引导状态 `octop_bot:onboarding:<uid>` | ✓ 跟着灵策账号走 | 登录了灵策：所有设备只引导一次（以云端那份为准）。只用本地账号：本机单独引导一次 |
| 本机账号密码、设备凭据、厂商 API Key、本机连接器凭据、本机电脑授权 | ✗ 永不上云 | |
| 本机 Bot 的一切 | ✗ 永不上云 | |

### 2.2 方向和冲突
- **云端是中心**：灵策账号在 bot.lynxce.cn 上就是一个租户，和现在一样。每台桌面是这个租户的一份副本：本机 Octop 里的同步程序带着灵策会话，从云端拉变更、把本机变更推上去。
- **变更流**：云端每个租户维护一个递增序号（新增一张 `sync_changes` 表，SQLite 和 PG 各一份迁移）。客户端只要报上次的游标，就拿到之后的增量；推送时每条带 `origin_id`，重复推送不会产生重复数据（沿用 8771b684 搬入接口「每条带来源」的做法）。
- **冲突**：
  - 消息只追加，按 id 合并，不会冲突。
  - **同一个会话同一时刻只有一处在跑回合**：开始一个回合前，先向云端申请这个会话的「运行租约」（大约 2 分钟，跑的过程中不断续期）。另一端看到「正在别处回复」，可以等它跑完，也可以停掉它。离线的桌面拿不到租约时照样跑，联网后把这一回合追加在后面，并且标注「离线回复」。
  - Bot 设置：每个字段后写入的覆盖先写入的（字段级 LWW，带版本号）。覆盖时在 Bot 资料页的「最近修改」里留一条记录。
  - 记忆：按条目 id 合并，删除用墓碑（tombstone）同步。

### 2.3 在手机或网页上「接着聊」时 Bot 在哪跑
- **云端跑**：手机和网页发的消息由云端 Octop 跑这一回合，用灵策模型（或这个账号保存的厂商 Key），需要电脑时用云电脑。**桌面离线也能聊**，这正是方案 C 的价值。
- 云端回合碰不到本机：本机文件、本机应用、本机连接器都用不了。Bot 需要这些时，给出一张「交给电脑」卡片（第三期），任务进入队列，桌面上线后由本机接着做，结果同步回来。第二期先简化成 Bot 直接告诉用户「这件事要在电脑上做」。
- 在桌面上发的消息永远由本机跑（隐私优先），默认用这台电脑；用户主动要求时才用云电脑（见 2.4）。

### 2.4 云电脑归属
- 云电脑属于灵策账号（云端租户），每个协同 Bot 一台。这和现在的租户模型一样，计费不变。
- 本机 Bot（🔒）没有云电脑，只用这台电脑。
- 桌面上跑的 Bot 也能用云电脑：2026-11-25 提前到第 1.5 期，做法见 §7。

### 2.5 和现有 bot.lynxce.cn 多租户云的关系
- 不动多租户：灵策账号在云端仍然是一个租户，网页和手机的用户继续直接用它。方案 C 只是让桌面成为这个租户的一份副本，外加同步接口：
  - `GET /api/octop-bot/sync/changes?after=`
  - `POST /api/octop-bot/sync/push`
  - `POST /api/octop-bot/sync/lease`
- 只用过网页或手机的老用户，装桌面并登录灵策后，他的 Bot 从云端拉下来，全部标为协同。

## 5. 风险
1. **隐私泄漏的口子**：协同 Bot 在本机读过的文件内容，可能以引用、摘要的形式出现在它的回复里，回复会上云。工具的原始输出虽然不同步，但模型自己写进回复的内容挡不住。缓解办法：打开同步开关时讲清楚；敏感的工作放在 🔒 Bot 上做。
2. **群组跨界**：混合群（本机 Bot 加协同 Bot）只能留在本机，用户可能以为手机上能看到。缓解：群头显示 🔒，并说明原因。
3. **双端同时跑**：租约过期、桌面离线回复，都可能让一个会话出现两条并行的回复。缓解：标注「离线回复」，不合并、不覆盖。
4. **数据库迁移**：新增同步表和每条记录的同步状态，要走编号迁移（SQLite + PG）。上游同步时要注意编号冲突，#3130 已经撞过一次。
5. **上游分叉**：本地账号恢复上游流程是好事，但 Octop Bot 的首启页要和上游的 setup 向导对齐，不能各写一套。
6. **计费**：桌面回合和云端回合都扣同一个灵策账号的积分，用量页要能按「本机 / 云端」区分，否则用户看不懂为什么关着电脑还在扣积分。
7. **灵策账号注销**：云端数据会按灵策的冷静期删除，本机副本保留并标为「已断开」。这一点要写进注销提示。

## 6. 已定（2026-11-25 用户确认：9 条全按建议）
1. **共存方式：按 Bot 分（有的本机、有的协同），还是整台电脑二选一？** 已定：**按 Bot 分**。这最符合「本地隐私隔离」：私密的事交给 🔒 Bot，需要手机接着聊的交给 ☁ Bot。
2. **登录灵策以后，新建的 Bot 默认是什么？** 已定：**登录前已有的 Bot 一律保持 🔒，不自动上云；登录后新建的 Bot 默认 ☁，创建时可以改**。手机和网页上建的 Bot 本来就是 ☁。
3. **工具调用的原始输出上不上云？** 已定：**不上**，只同步摘要。代价是云端接着聊时，看不到桌面回合里读到的原文。
4. **记忆同步：默认打开，还是默认关闭？** 已定：**打开**（Bot 换个端就失忆，体验很怪），但在同步开关旁边单独列一行，可以关掉。
5. **手机或网页接着聊时，桌面离线由谁跑？** 已定：**云端代跑**（方案 C 的价值就在这里），碰不到本机的事情说明一下，或者放进第三期的「交给电脑」。另一个选择是「只读，等电脑上线」，更保守，但手机基本用不起来。
6. **本地账号要不要每次输密码？** 已定：**只在首次设置时输**，之后靠设备凭据自动登录；改安全设置和远程访问时才要密码。
7. **只用灵策、不设本地密码，允许吗？** 已定：**允许**（本地账号在后台照样建好），但会持续提醒「为这台电脑设置密码」。
8. **新用户引导：跟着灵策账号只引导一次，还是每台设备各引导一次？** 已定：**登录了灵策就跟着账号走（只一次）**，没登录的本机引导一次。
9. **退出或切换灵策账号时，协同 Bot 怎么办？** 已定：**留在本机、标「已断开」**，不删除、不迁到新账号。

## 7. 桌面登录灵策后用云电脑（2026-11-25 提前，第 1.5 期）

起因：用户用正式版 1.0.5 桌面端登录灵策后，「Bot 的电脑」只有本机电脑控制，对话里也没有电脑图标，和网页、手机上的云端 Bot 不一样。用户的预期是：登录灵策就能用云电脑。目标是让登录灵策的桌面用户看到和网页、手机**一样的云电脑入口**：Bot 详情里的云电脑卡片、对话里的电脑图标和浮窗、点开才开机、接管、交还。

### 7.1 原则
- 腾讯云密钥不进客户端。云电脑由云 Octop（bot.lynxce.cn）统一开、统一计费，扣这个灵策账号的钱包，单价和网页上的云端 Bot 一样。
- Bot 的大脑（Agent 循环、工作区、对话）仍在本机，**只有「电脑」在云上**。本机文件只有在 Bot 明确传上去时才会上云电脑。
- 尽量复用：
  - 云端复用现有的 `ComputerManager`，所以开机、暂停、名额、闲置回收、磁盘费、扣费都不用重写。
  - 本机复用现有的 `computer_use_tool` / `request_takeover_tool` 和网页端的云电脑组件，只把它们底下的「管理器」换成一个远程版。

### 7.2 本机 Bot 在云端对应谁：影子 Bot
- 不另起一套「远程云电脑 key」（`docs/octop-bot-cloud-plan.md` §12.4 原来设想的 `/remote-computers/{key}`），而是在这个灵策账号的云端租户里，给每个要用云电脑的本机 Bot 建一个**影子 Bot**，也就是一行普通的 agents 记录：
  - `config_json.octop_bot.origin` = `<本机安装 id>:<本机 agent_id>`，同一来源只建一次；
  - `config_json.octop_bot.hidden` = true，云端 Bot 列表、手机和网页都不显示它；
  - 建好后不启动 Agent 运行时，只拿来挂云电脑。
- 好处：
  - 现有的 `/api/octop-bot/computers/{agent_id}` 全套接口（状态、一瞥、暂停、接管、画面票据、画面 WebSocket、粘贴和剪贴板）不用改，可以直接用；
  - 计费的 `computerId` 就是影子 Bot 的 id；
  - 名额按账号算，影子 Bot 和云端 Bot 一起占名额。
- 和第 2 期的关系：协同（☁）Bot 到第 2 期同步时，就用同一个 `origin` 把影子 Bot 转成正式的同步副本（去掉 hidden），云电脑原样保留，不白做。本机（🔒）Bot 的影子一直隐藏，只挂电脑，不带对话。
- 本机安装 id：本机 settings 键 `octop_bot:install_id`，第一次用时生成一个 ULID。

### 7.3 鉴权：本机怎么以这个灵策账号调用云 Octop
- 云 Octop 新增 `POST /api/auth/lynxce/token-login {access_token}`。传进来的是本机手上的**灵策 access token**（本机自己会续期），云端拿它去灵策查用户资料，按灵策账号找到租户，签发一个云 Octop 的 JWT。本机缓存这个 JWT，过期了就用新的 access token 再换一次。**不交出 refresh token**：CloudMove 的 `session-login` 会把本机的灵策登录态搬走，这里不能这样做。
- 云电脑扣费走租户**自己保存的灵策会话**（`Billing` → `lynxce_cloud.tenant_call`）。所以：
  - 用过网页或手机的账号已经有这个会话，直接能用；
  - 从没用过云端的账号（只有租户，没有会话，或者连租户都没有），`token-login` 返回 409 `BOT_CLOUD_SESSION_REQUIRED`。桌面弹一次「开通云电脑：再验证一次灵策账号」，用验证码或密码直接登录 bot.lynxce.cn 现有的灵策登录接口，云端就有了自己的会话。每个灵策账号只需要做一次。
  - 计划用灵策的一次性登录码（P17，灵策「岗位·后端与中台」在做）去掉这一步：本机用现有的灵策会话换一个一次性码，云端用这个码换一个属于自己的新会话保存起来，这样就不用弹窗。接口以灵策评审后的为准，定下来后再改这里。
  - refresh token 永远不交给云端。现有的 `session-login`（CloudMove 用的）等 P17 上线后删掉。

### 7.4 云 Octop 新增的接口（云端与计费）
现有的 `/api/octop-bot/computers/{agent_id}` 保留不动，另外新增：

| 接口 | 作用 |
|---|---|
| `POST /api/auth/lynxce/token-login` | 见 7.3 |
| `PUT /api/octop-bot/remote-bots/{origin}` | 按来源新建或更新影子 Bot（名字、头像），返回云端 `agent_id` |
| `DELETE /api/octop-bot/remote-bots/{origin}` | 本机删 Bot 时调用：释放云电脑，删除影子 Bot |
| `POST /api/octop-bot/computers/{agent_id}/run` | 执行命令：`{command, timeout}` → `{exit_code, output}`，走 `manager.run` |
| `POST /api/octop-bot/computers/{agent_id}/python` | 在云电脑上跑一段 Python，走 `manager.use(... run_python)`。电脑操作工具的点击、输入、等待、读取元素都用它 |
| `GET /api/octop-bot/computers/{agent_id}/screenshot` | 截图 PNG |
| `GET /api/octop-bot/computers/{agent_id}/accessibility` | 无障碍树 XML（点击前的付款和高风险检查要用） |
| `GET` / `PUT /api/octop-bot/computers/{agent_id}/files?path=` | 读写云电脑上的文件，用于本机工作区和云电脑互传 |

- 这些接口都要求是自己的 Bot（沿用现在 `_owned` 的检查），只在云端模式下开放，并且会让电脑开机（走 `ensure_running`）。
- 被接管时，`run` 和 `python` 返回「用户正在接管」，和 `CloudComputer.execute` 的处理一样。
- 影子 Bot 的回收：本机删 Bot 时会通知云端；本机卸载、长期不用时，按「影子 Bot 30 天没人用 → 释放云电脑并删除影子」处理。暂停期间按现有规则收磁盘费。

### 7.5 本机 Octop（桌面客户端）
- 新增 `infra/cloud/computers/remote.py`：
  - `RemoteComputerManager`：实现工具和路由用到的那部分 `ComputerManager` 方法，包括 `use`、`run`、`read`、`write`、`taken_over`、`set_takeover`、`pause`、`record`、`glance`、`claim_screen`、`note`、`activity`、`busy`。
  - `RemoteDriver`：`use(work)` 交给 `work` 的就是它，`screenshot`、`accessibility`、`run_python`、`run`、`read`、`write` 各对应 7.4 的一个接口。
  - 这样 `computer_use_tool`、`request_takeover_tool` 一行都不用改，就能用在本机 Bot 上。
- Bot 的电脑选择：Agent 的 `config_json.octop_bot.computer` = `"local"` 或 `"cloud"`。
  - 没有这个键时，☁ 协同 Bot 默认 cloud，🔒 本机 Bot 默认 local。
  - 没登录灵策时一律按 local，云电脑选项不出现。
  - 🔒 Bot 改成云电脑时提示一句：「Bot 在云电脑上看到和输入的内容会经过灵策云；这台电脑上的文件只有在 Bot 传上去时才会上云电脑。」
- 工具：
  - computer = cloud 时，挂 `computer_use_tool`、`request_takeover_tool` 和 `ComputerBriefing`（底下是 `RemoteComputerManager`），不挂本机应用控制工具。
  - 另外加一个 `cloud_computer` 工具：在云电脑上跑命令，以及在本机工作区和云电脑之间传文件。
  - Bot 自带的 `execute` 和文件工具仍然作用在本机工作区。
- 路由：桌面模式下，本机的 `/api/octop-bot/computers/{本机 agent_id}` 对 computer = cloud 的 Bot 转发到云端，也就是先换成影子 Bot 的 id，再调云端接口。画面 WebSocket 由本机中转：本机拿云端签发的一次性票据，自己连云端的 `/screen/ws`，再和网页对接。这样网页端的 `CloudComputerCard`、`CloudComputerFloat`、`CloudComputerScreen`、`CloudComputerHandoff` 组件不用改，还是同源调用。
- 入口开关：`/api/octop-bot/server-info` 的 `cloud_computer` 在桌面上「登录了灵策」时也是 true；另外每个 Bot 多返回一个 `computer` 字段。对话里的电脑图标、浮窗、Bot 详情里的云电脑卡片，按这个 Bot 的 `computer === "cloud"` 显示，本机电脑面板按 local 显示。
- 退出灵策时，先把所有影子 Bot 的云电脑暂停，再清掉本机缓存的云端 JWT。

### 7.6 和「云电脑用到才开」、名额、闲置回收、磁盘费的关系
- 这些全在云端的 `ComputerManager` 里，影子 Bot 和云端 Bot 走的是同一套，所以云端与计费正在做的方案 A（用到才开，点图标才开机）做完以后，桌面自动跟着生效，本机不用另写。
- **点图标才开机**：打开画面时，本机转发的画面票据请求就是一次「用到」。在这之前，对话里的电脑图标只显示「未开机」，不会去开机。
- **名额**：按灵策账号统计，影子 Bot 也占名额。名额满了，云端照现在的方式报错，本机把这个错误原样显示出来。
- **闲置回收、磁盘费**：照现有规则。本机断网或关机以后，云电脑会被闲置回收暂停，不会一直扣积分。

### 7.7 工作量和分工
- **云端与计费**：大约 2～3 天。
  - token-login 和 409 的处理；
  - remote-bots 的新建、更新、删除，以及 hidden 过滤（Bot 列表、群组成员选择、手机接口都要排除）；
  - 7.4 里的 run、python、screenshot、accessibility、files 几个接口；
  - 影子 Bot 30 天回收；
  - 测试。
  - 排在方案 A 之后，或者和方案 A 并行，两者改的地方不重叠。
- **桌面客户端**（local_f166a106）：大约 3～4 天。
  - `remote.py`（RemoteComputerManager 和 RemoteDriver）、JWT 缓存和「再验证一次」弹窗；
  - 路由转发和画面 WebSocket 中转；
  - 在 `agents/manager.py` 里按 computer 字段挂工具；
  - `cloud_computer` 工具；
  - 「Bot 的电脑」本机 / 云电脑选择，以及按 Bot 显示电脑入口。
  - 先按 7.4 的接口约定写，用假的云端接口测；云端接口上线后，再在 bot.lynxce.cn 上联调。
- **能不能不等第 2 期**：能。第 1.5 期只依赖第 1 期的 `octop_bot.sync` 来决定默认值，第 1 期还没合进去时，默认值先一律按 local，用户手动选云电脑。
- **另外的问题**：本机电脑控制一直黑屏转圈，这是本机画面权限或画面服务的问题，和本节无关，总管已另派桌面客户端查。

### 7.8 风险
1. **会慢一点**：每次电脑操作都多绕一跳，本机 → 杭州的 bot.lynxce.cn → 广州的 CVM，截图还要回传一次。可以接受；以后如果慢，就让本机直接连 CVM 的 443 端口，用云端签发的短期令牌。
2. **租户会话缺失**：没用过云端的账号第一次要再验证一次（7.3），这是方案里唯一多出来的一步。要让灵策提供「再开一个会话」的接口才能去掉。
3. **影子 Bot 混进列表**：凡是列 Bot 的地方都要排除 hidden，漏一处，手机上就会冒出一个空 Bot。测试要覆盖列表、群组、手机接口。
4. **两处同时操作一台电脑**：同一个影子 Bot 只被一台桌面使用，`claim_screen` 已经保证同一时刻只有一个会话在点。第 2 期以后，同一个 ☁ Bot 的云端回合和桌面回合会共用这台电脑，到时再复用 claim_screen 的规则。

### 7.9 安全要求（2026-11-25 按岗位手册第 18 条、安全审计第二节补充，安全岗已审）
§7 新增的接口都是对外接口，实现时按第 18 条执行：合并前要经安全岗评审。

**租户白名单**：云端租户能碰到的能力，一律按白名单设计，不靠「漏掉的就默认放开」。
- `remote-bots` 只接受名字和头像（头像要限制大小和类型）。影子 Bot 的 `config_json` 全部由服务端生成：后端固定用对象存储，不接受 `workspace_dir`、`memory.backend`、`acp` 或工具开关，客户端传了也直接忽略。
- 影子 Bot 只能用来挂电脑。启动 Agent、接收对话、改可见性、发布成模板、加进群组，这些接口遇到 hidden 的 Bot 一律拒绝。
- 按 hidden 过滤要走一个统一的查询入口，不在各个列表里各写一遍。
- `origin`：
  - 唯一键是 `(user_id, origin)`；
  - 格式只接受 `<ULID>:<agent_id>`，总长不超过 128；
  - 别的用户拿同一个 `origin` 来取，返回 404。
- 每个账号最多 20 个影子 Bot，同时也计入 `max_agents`。

**鉴权和归属**
- `token-login`：
  - 灵策 access token 只能放在请求体里，不写日志。服务端拿它去灵策查用户资料，取到灵策账号 id。
  - 按灵策账号 id 找租户；找不到就返回 409。不按邮箱或手机号去匹配，也不自动建租户。
  - 签出的 JWT 带单独的 purpose（例如 `desktop_remote`），有效期不超过 1 小时，不滑动续期。
  - 这种 JWT 只能调用 `remote-bots/*` 和 `computers/{id}/*` 这两组接口，拿去调别的接口一律拒绝。
  - 这个接口不进 JWT 豁免清单；如果非要加，只用精确路径，不用前缀。
- 电脑操作接口（run、python、screenshot、accessibility、files）沿用 `_owned` 归属校验。测试里要有一条「另一个用户来取，返回 404」。
- 本机缓存的云端 JWT 加密存在 `secret_repo` 里，不写日志，只放在请求头里，不进 URL。
- P17 的一次性码只在云端兑换。兑换后要核对灵策返回的用户 id，和租户绑定的是同一个账号。
- 管理员也不能悄悄操作别人的云电脑，要走有审计的运营接口。

**限流和上限**（测试里每一项都要有超限用例）
- `token-login`：按灵策账号、按来源 IP 分别限流。来源 IP 用修好审计 P0-9 之后的 `resolve_client_ip`。
- `remote-bots` 新建：按账号限流，总数受上面的 20 个限制。
- run 和 python：
  - timeout 不超过 300 秒，输出截断到 1 MB；
  - 每个账号同时最多跑 2 个；
  - 每次调用记一条审计，命令只记前 200 个字。
- files：单个文件不超过 50 MB，上传和下载都流式转发、边读边限，先校验归属再读请求体。

**画面**
- 本机中转画面 WebSocket 时，用云端签发的一次性画面票据（现有的 `_tickets`）去连，云端 JWT 不放进 WebSocket 的 URL。
- 画面会话令牌按审计 P1-6 的修法走：放在请求头里，设绝对过期时间，WebSocket 断开就作废。本机中转也照这个做。

**资源**
- 云电脑按用户限制同时运行的台数（按定价表）。`_make_room` 只暂停同一用户的电脑（审计 P1-8）。影子 Bot 的电脑和云端 Bot 的电脑合在一起算。
- 影子 Bot 30 天没人用就回收。这条规则也防止卸载了客户端的账号一直占着磁盘。

**云电脑本身**
- run 和 python 只在这个用户自己的云电脑上执行，绝不在云 Octop 的宿主机上执行。实现时直接调 `ComputerManager.run` / `use`，不经过 harness 的任何本地执行工具。
- 云电脑上没有平台密钥：开机时 user data 里只写这台机器自己的访问令牌。CVM 不挂 CAM 角色。
- 安全组禁止同组实例互相访问，一个用户的云电脑连不到别人的。
- 云 Octop 连 CVM 时，除了校验证书是不是私有 CA 签的，还要校验证书里的实例标识和要连的那台对得上（`cvm.py` 里现在只校验 CA）。
